# Sources and ingestion policy

Use Wikidata (structured facts, CC0), Wikipedia (fact checking and pointers; prose licensing requires care), Wikimedia Commons (per-file license), official cemetery material, and public historical records. Do not scrape Find a Grave, BillionGraves, or other third-party cemetery directories. Link to sources; never copy biographies wholesale.

Every factual seed field needs traceable evidence. Record retrieval time, URL, field scope, confidence, and entity association. Editorial descriptions and Dead Scores must be distinguished from imported facts. Unknown date components and images remain absent. Coordinates require separate verification from burial membership.

Development seeds will be committed and usable offline. Unverified data must remain labeled fixtures with draft status and no public read access. Public release requires source/coordinate review and licensed images. A cemetery center is not an entrance or exact grave; future directions must explain that distinction.

## Ingestion (Milestone 7)

`npm run ingest:wikidata -- [--limit N] [--radius-km N] [--lat N --lon N --label "City, ST"]` (default 25 people, 40km, Detroit; hard ceiling 100 — a proof of concept, not a national importer) queries Wikidata's public SPARQL endpoint for deceased people (`wdt:P31 wd:Q5`) with a documented place of burial (`wdt:P119`) whose coordinates fall within the given radius of the target city, via Blazegraph's `wikibase:around` geospatial service. The city center is a CLI argument, not a hardcoded constant, specifically so the same proof of concept can be pointed at other cities without code changes. That one query returns name, birth/death dates, the burial place and its coordinates, a Wikipedia URL, and a Commons image filename — everything the pipeline needs from exactly one HTTP request, regardless of result count. Requests identify themselves with a real User-Agent per Wikimedia's User-Agent policy and retry on 429/5xx with backoff, honoring `Retry-After` when the endpoint sends one.

Occupation is deliberately not fetched. It would need multi-value aggregation for a field with nowhere to go: category assignment is an editorial decision (see below), never derived automatically from Wikidata's occupation ontology.

Results are normalized (`src/lib/ingestion/normalize.ts`) and deduplicated (`src/lib/ingestion/dedupe.ts`) against the existing seed by `wikidata_id` first, then by a generated slug — a slug match is flagged `possible_duplicate` with a reason, never silently merged. Run live against Detroit, this correctly caught Aretha Franklin, James Jamerson, and David Ruffin as already in the seed, while surfacing genuinely new real people with a documented burial nearby (Erma Franklin, C. L. Franklin, Barrett Strong, David Dunbar Buick, Henry M. Leland, among others) — a real proof, not a hypothetical one. The run is written to `data/ingestion-runs/<uuid>.json` (gitignored — raw fetch output is not reviewed content) with a run ID, query description, and every candidate's source URL for later auditing. Nothing is written to any database by this step.

A raw candidate cannot become a real `people` row on its own: the schema requires a human-written `short_description` (1–500 characters, `not null`), and this project will not fabricate one to make ingestion look more automated than it is. `src/lib/ingestion/reviewed.ts` defines what a candidate needs after a human has actually reviewed it — `short_description`, at least one category, a Dead Score, and an explicit `confirmed: true` that is not a default a reviewer can leave in place by accident. `npm run publish:reviewed -- <file> --confirm` (`scripts/publish-reviewed-candidates.ts`) takes a copy of a run file that has been edited to add those fields, validates every candidate before writing anything, and upserts each as `status='draft', is_fixture=false` — a real draft record, but never published. Publication stays the separate, later, human action it already was for the seed (see docs/DATABASE.md). This script requires `SUPABASE_SERVICE_ROLE_KEY`, since RLS grants anon/authenticated read-only access. It has since been run for real against the live FindTheDead project: David Dunbar Buick and Henry M. Leland (real Detroit automotive figures, both genuinely new — neither was in the dev seed, and neither was their cemetery, Woodmere) were reviewed by hand, published as drafts, and — on the product owner's explicit direction — published for real shortly after (see the note on the seed below and docs/ROADMAP.md).

A known, documented limitation: Wikidata's SPARQL results don't expose date precision, so a year-precision date ("just 1942") is indistinguishable from a genuine January 1st and is treated as imprecise (year kept, exact date dropped) — a heuristic, not a guarantee a reviewer should skip checking. Commons image filenames are captured but never inserted into `images`: resolving an actual license and attribution needs a separate Commons API call this proof of concept does not make, and per this document's own policy, no image is publishable without that metadata.

## Statewide Michigan expansion

`npm run ingest:michigan` runs the same bounded discovery process across 14 underserved regional hubs in the Upper Peninsula, northern Lower Peninsula, West Michigan, Mid Michigan, and eastern Michigan. It deliberately excludes the five launch metros already reviewed. Candidate burial coordinates are filtered through a simplified official U.S. Census TIGERweb Michigan state boundary before deduplication; this prevents border hubs from silently importing cemeteries in Indiana, Wisconsin, or Ontario without making Wikidata's slower administrative-property traversal part of every query. The boundary was retrieved from the Census Bureau's `TIGERweb/State_County` service (States layer, Michigan GEOID 26, WGS84, 0.01-degree simplification) on 2026-09-06 and is stored at `data/michigan-boundary.json`. Results are checkpointed after every regional hub, combined into one review file, and deduplicated both within the batch and against people visible through the live public database, in addition to the original seed. The command makes no database writes and does not publish anything.

Statewide means statewide editorial coverage, not thin city pages or an unreviewed bulk import. Candidates still need a real article/source review, original biography and hook, categories, Dead Score, burial-location check, and explicit publication approval. Regional hubs are only search centers for finding candidates; they are not automatic landing pages and do not imply that every town inside a radius has been fully covered.

The first corrected statewide sweep found 317 Michigan candidates after excluding 35 cross-border results; 316 were new to the public collection. A balanced first wave of 30 was then reviewed and saved at `data/reviewed-runs/michigan-statewide-wave-1.json`. Every selected person has an original biography and hook, a revision-pinned personal source, reviewed categories and Dead Score, and a specific Michigan burial place. The batch adds meaningful representation in the Upper Peninsula, northern Lower Peninsula, West Michigan, Mid Michigan, and the east side without automatically publishing the other 286 candidates.

## Initial seed review — 2026-09-05

`data/detroit.seed.json` contains 22 real deceased people and two Detroit cemeteries, not invented identities. Names, known years, brief factual occupation labels and burial membership were checked against these revision-specific reference lists:

- [Woodlawn Cemetery](https://en.wikipedia.org/w/index.php?title=Woodlawn_Cemetery_(Detroit)&oldid=1365624171): 12 people; cemetery reference coordinate 42.4419, -83.1261.
- [Elmwood Cemetery](https://en.wikipedia.org/w/index.php?title=Elmwood_Cemetery_(Detroit)&oldid=1372400484): 10 people; cemetery reference coordinate 42.34722, -83.01861.
- [Official Woodlawn site](https://www.woodlawncemeterydetroit.com/) additionally names Aretha Franklin, Rosa Parks, the Dodge brothers, Edsel Ford, James Jamerson, David Ruffin and Levi Stubbs among those resting there.

Original short labels summarize factual roles; no biographies or images were copied. Category assignments, featured flags, confidence values and Dead Scores are provisional editorial decisions, not sourced metrics. The cemetery-listing citation URLs above are reference evidence for burial membership, not personal Wikipedia URLs or Wikidata IDs — see the profile enrichment note below for those.

All seed entities were originally drafts with `is_fixture=true` (meaning development-only, not fictitious) — this is a source-backed starter set, not a publication-grade fact-check, and the caution here was to confirm burial membership with official records and validate coordinate precision/access before publishing it. The public read role correctly returned no development records while that held.

On 2026-09-05 the product owner explicitly directed publishing this set as-is, on the strength of the review already documented above, rather than commissioning a separate official-records pass first. All 22 seed people plus the two Wikidata-sourced additions (24 total) and all 3 cemeteries are now `status='published', is_fixture=false` and visible through the public read role — see docs/ROADMAP.md for what was verified afterward. No exact graves or entrance coordinates are asserted for any of them; every burial remains `location_precision='cemetery'`.

## Profile enrichment — 2026-09-06

Each of the 22 seed people originally shipped with `birth_date`, `biography`, and `why_interesting` all null — the initial review only established years and a one-line factual label, sourced to the *cemetery's* Wikipedia article, not the person's own. This pass fetched each person's own English Wikipedia article (a stable revision, pinned by `oldid`, recorded per-person as the new `profile_source_url` field in `data/detroit.seed.json`), extracted their exact birth date where the article gives day/month precision, and wrote an original, paraphrased biography paragraph and a one-line editorial hook (`why_interesting`) from those facts — never copying Wikipedia's own prose. `scripts/build-seed.ts` now emits a third `sources` row per person (field `birth_date,biography,why_interesting`) pointing at `profile_source_url` when one exists, alongside the original two rows (cemetery-listing facts, burial).

Two documented exceptions, consistent with this project's refusal to invent precision it doesn't have:

- **James Jamerson**: the seed's `birth_year` (1938) and English Wikipedia's infobox (January 29, 1936) disagree — a real, unresolved discrepancy noted by biographers, not a typo. `birth_date` stays null; the biography paragraph names the discrepancy explicitly rather than silently picking a side.
- **George M. Holley Sr.**: no standalone Wikipedia biography exists for him. His `profile_source_url` instead cites the [Holley Performance Products](https://en.wikipedia.org/w/index.php?title=Holley_Performance_Products&oldid=1370417128) company article, the most substantive verifiable secondary source that discusses him personally (founding story, inventions, later career) — sufficient for a biography, but without a specific birth-date day/month, so `birth_date` stays null.

This did not touch `birth_year`, `death_year`, `short_description`, `dead_score`, `categories`, or burial/cemetery data from the original review — only the three fields that were always meant to await "profile research" (see above).

`npm run seed:build` validates JSON, uses stable IDs, escapes SQL literals, and generates `supabase/seed.sql`. It performs no network access or database writes. `npm run seed:check` detects drift. Reapplying SQL is idempotent; existing rows are not overwritten. Source records target each person, burial, and cemetery through actual foreign keys. Never seed production; these fixed IDs are reserved for development.
