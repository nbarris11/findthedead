# Roadmap

National collection update (2026-09-09): a resumable collector has completed all 50 states and DC, producing a local review library of 97,165 unique candidate people and 97,439 burial claims. It includes Census state/county matching, public-profile deduplication, dense-area pagination, and separate research/evidence caches. All 51 searches completed without pending or capped queries. This does not expand the public site automatically; the next editorial step is selecting and verifying national release batches. See `docs/NATIONAL-COLLECTOR.md` and `data/ingestion-runs/us-national/REPORT.md`.

1. Foundation: Next.js, TypeScript, Tailwind, layout, minimal homepage, metadata, documentation, environment template. Validate lint/typecheck/build and HTTP response. Commit independently.
2. Database: Supabase/PostGIS migrations, constraints/RLS/indexes, typed contracts, bounded geographic RPCs, 20–50 sourced development records, deterministic seed tooling and critical tests. Validate offline and SQL where local PostGIS is available. Commit independently.
3. Explore: Mapbox native clustering, filters, bounds search, location/errors, accessible mobile preview sheet. Install Mapbox here.
4. Nearby: permission flow, radii, sorting and distances with manual fallback.
5. Profiles: people/cemeteries, sources, precision-aware maps/directions, nearby records, substantive SEO.
6. Search: performant person search; cemetery query contract and distinct result types.
7. Ingestion: bounded Wikidata proof of concept, provenance, normalization and deduplication.

Never combine unrelated work into one commit. Preserve the next milestones until the schema and development flow are stable.

Launch readiness: real-database tests, evidence review, publication, and desktop/mobile browser QA are complete. SEO is enabled only for the homepage and published person/cemetery profiles, with a database-generated sitemap and robots file; utility routes remain noindex. Licensed profile images are now supported and the second statewide batch includes 38 of them. Remaining work: continue photo coverage for text-only profiles, add observability without location leakage, validate real-device location permission behavior, and connect/verify the final custom domain. Authentication/admin/tours are separate later decisions.

## Foundation delivery status

All seven milestones are implemented. Milestone 1 was committed as `18456fb`; Milestone 2 as `07155d8`; Milestone 3 as `431a0eb`; Milestone 4 as `1f40cf3`; Milestone 5 as `58a2e84`; Milestone 6 as `a4de1e8`. Milestone 2 adds 22 sourced development people, two cemeteries, 10 categories, 46 provenance records, protected geographic RPCs, an explicit offline repository, and database-backed featured reads. Milestone 3 adds `/explore`: a bounded `GET /api/people/bounds` route handler, Mapbox GL native clustering (no per-marker React nodes), a data-driven category/notable filter bar, an accessible bottom sheet with precision-aware directions, a cluster-to-list fallback for coincident cemetery-precision burials, geolocation with distinct denied/unavailable/loading states, and a token-less fallback list so the route degrades instead of breaking.

Milestone 4 adds `/nearby`: a `GET /api/people/nearby` route handler over the existing `nearbyPeople` repository function, an explicit location-permission gate with a manual "Browse Detroit instead" fallback, radius selection (5/10/25/50 mi), and client-side nearest/most-notable/recently-added sorting. Exposing `created_at` through `discovery_people` and `nearby_people` (migration `20260905190000_expose_created_at.sql`) was the one schema change this milestone needed; see docs/DATABASE.md for why it isn't backdated or fabricated per person.

Milestone 5 adds `/people/[slug]` and `/cemeteries/[slug]`: real pages behind every "View profile" link and cemetery link already written into Explore, Nearby, and each other. `personProfile`/`cemeteryProfile` read the base tables directly for fields no discovery feed carries (biography, external IDs, full provenance), reusing `discovery_people` for the parts it already solves. One new function, `cemetery_by_slug` (migration `20260905200000_cemetery_by_slug.sql`), exposes a cemetery's own coordinate for its map. Both pages carry canonical URLs, Open Graph, and Person/Cemetery JSON-LD. Following editorial review and publication, these public profiles are indexable and included in the generated sitemap; missing records and utility routes remain noindex.

Milestone 6 adds `/search`, matching the spec's own explicit initial scope: performant, debounced person-name search, per-word prefix matching so a partial name matches while still typing. One new function, `search_people` (migration `20260905210000_search_people.sql`), is the first consumer of the `people_name_search` GIN index that has existed unused since Milestone 2. The result type is already a person/cemetery discriminated union (`src/lib/search/types.ts`) with a card renderer that switches on it, even though only person search is implemented — per the spec, cemetery/city/occupation search is explicitly "eventually," not this release.

Milestone 7 adds the bounded Wikidata ingestion pipeline: `npm run ingest:wikidata` (fetch/normalize/dedupe, writing a reviewable run file, never touching a database) and `npm run publish:reviewed` (the separate, human-gated, `service_role`-only step that upserts drafts from a run a person has actually reviewed and enriched with the editorial fields — `short_description`, categories, Dead Score — that Wikidata cannot supply). One new function, `set_cemetery_location` (migration `20260905220000_set_cemetery_location.sql`), gives the PostgREST-based publish path a way to write PostGIS geography it otherwise couldn't express. The fetch pipeline was run live against the real Wikidata endpoint (not just unit-tested) and correctly identified Aretha Franklin, James Jamerson, and David Ruffin as already in the seed while surfacing genuinely new real people — see docs/DATA-SOURCES.md for the full run. All seven milestones from the original spec are now delivered.

## Deployment status

The app is live on Netlify at `findthedead.netlify.app`, connected to `github.com/nbarris11/findthedead` (public) for continuous deployment on every push to `main`. `netlify.toml` was committed before the first deploy so the build config is version-controlled, not click-configured. Environment variables were set via Netlify's dashboard (imported from a `.env`-shaped paste, not typed one at a time) and a fresh deploy triggered afterward to pick them up. Verified directly against the live deployment, not just assumed from a successful build: `/`, `/explore` (map tiles and clustering actually render through Netlify's serverless Next.js function), `/search`, `/nearby`, and a genuine `/people/[slug]` 404 all checked in an unauthenticated browser session, console clean.

This surfaced one real bug: `dataConfig`'s demo-mode safety guard checked `VERCEL_ENV === "production"` specifically — a platform variable Netlify never sets, so the guard would have silently done nothing on this host. Fixed to check `NODE_ENV === "production"` instead, which every host sets for a production Next.js build regardless of platform (`src/lib/data/config.ts`).

`SUPABASE_SERVICE_ROLE_KEY` was deliberately not set on Netlify — the running app never needs it, only the offline ingestion scripts do — keeping the deployed app's credential surface to exactly the anon publishable key.
